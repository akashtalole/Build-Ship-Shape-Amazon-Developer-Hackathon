    StudyLoop — Ambient Study Session Coach for Bee¶

    Implementation of the "StudyLoop" idea from hackathon-ideas/bee.md: students lose track of what they actually discussed or decided in a study session, and converting ambient conversation into structured review material is friction they mostly skip. StudyLoop takes a study session's transcript, turns it into a short summary plus a set of spaced-repetition flashcards automatically, and schedules them into a daily review queue — no manual note-taking required.

    Built for the Bee track of the Build, Ship, Shape: Amazon Developer Hackathon, which requires data from a real Bee wearable (or an Apple Watch running Bee software) and guides teams to integrate Bee's CLI, MCP server, or Agent Skills, prioritizing education, developer experience, and productivity.

    Scope of this submission¶

    This environment has no physical Bee device or Apple Watch, so this repo implements the backend service that would sit behind Bee's ambient capture — the part of StudyLoop that is genuinely testable headlessly: ingesting transcript segments, generating flashcards/summaries from them, and running the spaced-repetition scheduler that decides what to review and when. That pipeline is real, tested, and independent of where the transcript came from.

    What stands in for Bee, and what a real integration looks like¶

    POST /sessions accepts a raw transcript directly (a text block, or an array of {speaker, text, timestampMs} segments) — standing in for what Bee's MCP server or CLI would hand off after a study session ends. That normalization is isolated in one function, normalizeTranscript in src/studyService.ts, which is explicitly documented as the integration seam:

    • Today: a caller (a script, a curl command, a UI) posts a transcript straight to POST /sessions.
    • With real Bee integration: instead of a human/UI posting a transcript, a small sync job would call Bee's transcript-retrieval MCP tool (e.g. a get_transcript-style tool for a session or time range) — which already returns diarized, timestamped segments in the same {speaker, text, timestampMs} shape defined in src/types.ts — and pass that array straight into normalizeTranscript/ingestSession. The array branch of normalizeTranscript is the real integration path already; only the string-splitting branch (a convenience for pasting raw text by hand, used here so the API is testable without Bee) would become dead code.
    • Nothing in flashcardGenerator.ts, scheduler.ts, studyService.ts, or server.ts needs to change to wire in the real source — they only ever see TranscriptSegment[].

    How it works¶

    1. Ingest a session (POST /sessions) — post a transcript (string or segments). StudyLoop normalizes it, generates a summary and a set of flashcards, and stores them.
    2. Generate flashcards/summary — src/flashcardGenerator.ts defines an LLM-shaped FlashcardGenerator interface and ships TemplateFlashcardGenerator, a heuristic implementation with no model dependency: it pairs question/answer exchanges, extracts definition-style statements ("X is/means/refers to Y"), and falls back to cloze-deletion cards from the longest sentences so a session with neither still yields review material.
    3. Schedule review — each flashcard gets spaced-repetition state (interval, ease factor, repetitions, due date) from a simplified SM-2 algorithm in src/scheduler.ts, as pure functions.
    4. Review daily (GET /review/due) — the flashcards due today, across every session, oldest-due first.
    5. Submit a grade (POST /review/:cardId) — again / hard / good / easy; the scheduler reschedules the card's next due date and returns its updated interval/ease factor.

    A second pass added six more production-grade pieces on top of that pipeline — idempotent retries, leech detection, topic tagging + search, adaptive review ordering, incremental/streaming ingestion, and a portable export — each described in detail in Advanced features below.

    Running it¶

    npm install
npm run build
npm start
# StudyLoop listening on http://localhost:4466

    Or for local iteration: npm run dev

    Try it by hand¶

    # 1. Ingest a study session transcript (stands in for a Bee ambient capture pull)
curl -X POST localhost:4466/sessions -H "Content-Type: application/json" -d '{
  "title": "Bio 101 study group",
  "transcript": [
    {"speaker": "Alice", "text": "Mitochondria is the powerhouse of the cell."},
    {"speaker": "Bob", "text": "What is the powerhouse of the cell?"},
    {"speaker": "Alice", "text": "The mitochondria is the powerhouse of the cell."}
  ]
}'
# -> note the session id and the generated flashcard ids in the response

# 2. See the session's summary and flashcards again
curl localhost:4466/sessions/<sessionId>

# 3. Check today's review queue (freshly generated cards are due immediately)
curl localhost:4466/review/due

# 4. Submit a recall grade for a card ("again" | "hard" | "good" | "easy")
curl -X POST localhost:4466/review/<cardId> -H "Content-Type: application/json" -d '{"grade": "good"}'
# -> the response shows the new interval/dueAt; review again with "again" to see it drop back down

    Testing¶

    npm test

    Starts the server on an ephemeral port and drives it over real HTTP requests: ingesting a transcript produces a non-empty summary and at least one flashcard; a fresh card appears in GET /review/due; a good grade grows its interval and moves it out of today's queue; consecutive good grades keep growing the interval; an again grade resets the streak and shortens the interval back down instead of continuing to grow it; reviewing an unknown card id or fetching an unknown session id returns a clean 404; an invalid grade returns a 400; an empty/whitespace-only transcript still returns a sensible response (a fallback summary, zero flashcards) instead of crashing; and a raw text-block transcript (not pre-segmented) is ingested successfully too. A couple of direct unit-style checks of scheduler.ts's interval/ease-factor math round it out. Every feature in Advanced features, Round 3, Round 4, and Round 5 below has its own passing HTTP-level check plus, where the logic is pure, a direct unit-style check — see the "Feature N" tests in test/smoke.test.ts.

    Advanced features¶

    A second implementation pass added six production-grade features on top of the v1 pipeline above. Each is independently tested in test/smoke.test.ts (search for "Feature 1" through "Feature 6").

    1. Idempotent session ingestion¶

    POST /sessions accepts an optional idempotencyKey (or externalSessionId, treated as an alias — pass whichever you have). Re-posting the same transcript with the same key returns the original session and flashcards — same ids, no regeneration — instead of creating a duplicate study set. This is what makes a retried upload (a flaky connection, an at-least-once sync queue, a doubled tap on "sync now" in a companion app) safe to replay. The mapping from key -> session id lives in store.ts; studyService.ingestSession checks it before doing any generation work at all.

    curl -X POST localhost:4466/sessions -H "Content-Type: application/json" -d '{
  "title": "Bio 101 study group",
  "idempotencyKey": "sync-job-run-482",
  "transcript": "Osmosis is the movement of water across a semipermeable membrane."
}'
# Re-run the exact same request (same idempotencyKey) any number of times —
# the response always has the same session.id and flashcard ids, never a duplicate.

    2. Leech detection¶

    Every flashcard tracks consecutiveFailures (consecutive "again" grades) and isLeech (true once that streak hits LEECH_THRESHOLD, currently 3 — see leech.ts). A single subsequent "good" or "easy" grade clears the flag and resets the streak; a "hard" grade neither advances nor resets it (it's a lukewarm pass, not a failure). Leeches are surfaced on their own endpoint, GET /review/leeches, distinct from the general due queue, so a student can see which cards need to be reformulated rather than endlessly rescheduled — SM-2's core blind spot.

    # Grade the same card "again" three times in a row...
curl -X POST localhost:4466/review/<cardId> -H "Content-Type: application/json" -d '{"grade": "again"}'
curl -X POST localhost:4466/review/<cardId> -H "Content-Type: application/json" -d '{"grade": "again"}'
curl -X POST localhost:4466/review/<cardId> -H "Content-Type: application/json" -d '{"grade": "again"}'
# -> the response now has "isLeech": true, "consecutiveFailures": 3

curl localhost:4466/review/leeches
# -> a list of every currently-flagged leech, across every session

curl -X POST localhost:4466/review/<cardId> -H "Content-Type: application/json" -d '{"grade": "good"}'
# -> "isLeech": false, "consecutiveFailures": 0 — one solid recall clears it

    3. Topic tagging + search¶

    When a session is ingested (or extended — see Feature 5), topics.ts extracts 1-3 heuristic topic tags from the full transcript and attaches them to every flashcard generated at that point. This is explicitly a heuristic, not real NLP or topic modeling: it scores each content word (length >= 4, not a stopword) by raw frequency, with a small bonus for words that appeared capitalized in the original text (a cheap proxy for proper nouns/key terms), and returns the top-scoring 1-3 as lowercase tags. It reliably picks out the term a session was about ("ribosome," "mitochondria") when that term is repeated, and does nothing cleverer than that. GET /flashcards/search?topic= then finds every flashcard across every session carrying a given tag, so a student can pull together material on the same topic even when it came from separate study sessions weeks apart.

    curl "localhost:4466/flashcards/search?topic=ribosome"
# -> every flashcard, from any session, whose extracted topics include "ribosome"

    4. Adaptive review ordering¶

    GET /review/due no longer returns cards in plain due-date order — it ranks them by a priority score (see priority.ts, doc-commented in full there):

    score = overdueDays * OVERDUE_WEIGHT           (OVERDUE_WEIGHT = 1)
      + (isLeech ? LEECH_BONUS : 0)            (LEECH_BONUS   = 10)
      + max(0, BASELINE_EASE - easeFactor)      (BASELINE_EASE = 2.5)
        * EASE_WEIGHT                           (EASE_WEIGHT   = 2)

    overdueDays rewards cards that have been put off longer; the leech bonus is a large flat addition (worth ~10 days of plain overdue-ness) so a leech surfaces near the top of the queue almost regardless of its due date, because the whole point of leech-flagging is forcing it in front of the student instead of letting it get quietly rescheduled forever; the ease term gives a smaller boost to cards that have historically been hard to recall (a below-baseline SM-2 ease factor), since that's a real but softer signal than 3-in-a-row failures. Cards that aren't due yet are still filtered out first — this only reorders the pool that's already eligible today.

    curl localhost:4466/review/due
# -> due cards sorted by priority score descending: a leech, or a badly overdue/hard card, first

    5. Streaming/incremental ingestion¶

    PATCH /sessions/:id/segments appends newly-captured transcript segments to an already-ingested session — the same shape POST /sessions accepts (a string, or an array of {speaker, text, timestampMs} segments) — mirroring Bee's continuous ambient capture (many small updates over the course of a session) rather than one big batch upload after the fact. It regenerates the session's summary and topic tags from the full updated transcript, but only persists flashcards that weren't already generated for this session (deduped by front text), so re-running the generator over the combined transcript doesn't re-mint duplicates for material it already produced a card from earlier.

    curl -X PATCH localhost:4466/sessions/<sessionId>/segments -H "Content-Type: application/json" -d '{
  "segments": [
    {"speaker": "Alice", "text": "Active transport moves molecules against a concentration gradient using energy."},
    {"speaker": "Bob", "text": "What is active transport?"},
    {"speaker": "Alice", "text": "It requires ATP to move against the gradient."}
  ]
}'
# -> { "session": { ...updated summary/segments/topics... }, "newFlashcards": [ ...only the new cards... ] }

    6. Portable export¶

    GET /sessions/:id/export (one session) and GET /export (every session) return every flashcard as a flat TSV — tab-separated rather than comma-separated because flashcard text routinely contains commas, which would otherwise need quoting. Three columns, with a header row: front, back, tags (space-separated, matching Anki's own multi-value tag convention).

    curl localhost:4466/sessions/<sessionId>/export
# front back    tags
# What is a ribosome?   Ribosome function is essential for protein synthesis.   ribosome protein
# ...

    To import into Anki: File -> Import, set "Fields separated by" to Tab, map column 1 -> Front, column 2 -> Back, column 3 -> Tags, and tell it to skip the header line.

    Swapping in a real LLM-backed generator¶

    Everything in server.ts and studyService.ts depends only on the FlashcardGenerator interface in flashcardGenerator.ts (generate(segments) -> {summary, flashcards}), not on TemplateFlashcardGenerator specifically. To go from heuristic to model-backed:

    1. Implement FlashcardGenerator with a class that sends the segments to a model — e.g. Amazon Bedrock (natural pairing with the hackathon's AWS Builder mini-challenge) — with a prompt like "extract key facts and Q&A pairs from this study session transcript and return JSON {summary, flashcards: [{front, back}]}", then parses and validates the model's JSON response into that same shape.
    2. Swap the generator instance constructed in src/index.ts (and in tests, if desired) from new TemplateFlashcardGenerator() to new LlmFlashcardGenerator(bedrockClient).

    No change to studyService.ts, scheduler.ts, or server.ts is needed — that's the point of isolating generation behind an interface from the start.

    Judging-criteria alignment¶

    • Tech Implementation: The three real seams a production build would need — Bee transcript ingestion, LLM-backed generation, and spaced-repetition scheduling — are each isolated behind a small interface (normalizeTranscript's segment shape, FlashcardGenerator, and pure functions in scheduler.ts), so swapping the heuristic generator for Bedrock or wiring in Bee's real MCP tool is a scoped, single-file change, not a rewrite. The scheduler itself implements real SM-2 mechanics (interval growth, ease factor, repetition streak reset on failure), not a placeholder. The advanced round adds real production concerns on top: idempotent ingestion (safe retries), a leech-detection state machine, a documented multi-signal priority formula for review ordering, incremental ingestion that dedupes against already-generated material, and a portable export format — each isolated in its own small module (leech.ts, priority.ts, topics.ts, export.ts) and covered by its own passing test, not bolted on as a demo-only stub.
    • Design: Zero manual note-taking — a transcript in, a summary and review-ready flashcards out. The daily review surface (GET /review/due) is a single endpoint by design, matching the idea's "clean daily review flow" goal; a companion app would render it directly with no extra aggregation logic needed.
    • Potential Impact: Directly hits "education," one of the Bee track's three explicitly prioritized categories, with an everyday, recurring use case (students studying together, or half-remembering a lecture) rather than a one-off demo scenario.
    • Quality of Idea: Goes beyond a transcript viewer or generic summarizer by closing the loop into an active learning system — extraction feeding a real scheduling algorithm that adapts to how well material was recalled, which is what makes it a study coach rather than a note-taking tool. Round 5 pushes this further with four features that go beyond "more infrastructure": a concept graph built from real text analysis (not manual tagging) that links material across separate sessions/decks; a genuine Feynman/peer-teaching mode with a real key-term rubric wired into the same scheduling machinery as a normal grade; cross-session study-guide synthesis that deduplicates rather than concatenates; and a composite, explainable exam-readiness score — each a capability a student would actually reach for, not a demo-only stub.

    Round 3: quiz mode, shared decks, reminders, adaptive generation bias¶

    A third pass added four more features, each independently tested in test/smoke.test.ts (search for "Feature 7" through "Feature 10").

    7. Shared study-group decks¶

    POST /sessions accepts an optional shared: true, marking the resulting session as a shared study-group deck. Another student — identified by nothing more than a caller-supplied studentId string, no auth for this demo — can then call POST /decks/:sessionId/join to pull that session's flashcards into their own personal review queue. Critically, the flashcard content (front/back/tags) is never copied or regenerated: only a fresh, independent review-state row (interval, ease factor, repetitions, due date, leech tracking) is created per (studentId, card) pair. Two students who join the same deck and review the same card end up with completely independent ease factors, due dates, and leech flags — one can leech a card while the other aces it, and neither touches the card's own embedded (student-less) state, which is what every original, studentId-less endpoint still reads and writes. GET /review/due, GET /review/leeches, and POST /review/:cardId all accept an optional studentId (query param for the GETs, body field for the POST) to operate on that student's own state instead of the shared default.

    # Ingest a shared deck
curl -X POST localhost:4466/sessions -H "Content-Type: application/json" -d '{
  "title": "Bio 101 study group", "shared": true,
  "transcript": "Meiosis is the process of cell division that produces gametes."
}'
# -> note the session id

# Two different students join the same deck
curl -X POST localhost:4466/decks/<sessionId>/join -H "Content-Type: application/json" -d '{"studentId": "alice"}'
curl -X POST localhost:4466/decks/<sessionId>/join -H "Content-Type: application/json" -d '{"studentId": "bob"}'

# They review the same card independently
curl -X POST localhost:4466/review/<cardId> -H "Content-Type: application/json" -d '{"grade": "easy", "studentId": "alice"}'
curl -X POST localhost:4466/review/<cardId> -H "Content-Type: application/json" -d '{"grade": "again", "studentId": "bob"}'
# -> alice's and bob's responses show different easeFactor/dueAt/isLeech on the *same* cardId

curl "localhost:4466/review/due?studentId=alice"   # alice's own due queue
curl "localhost:4466/review/leeches?studentId=bob" # bob's own leeches

    8. Quiz/practice-test mode¶

    POST /quiz/start { count, studentId? } samples up to count cards into a new timed quiz. Sampling reuses the exact same due-filtering (isDue) and priority-ranking (priorityScore/sortByPriority) logic GET /review/due is built on — due cards come first, worst-priority (leeches, overdue, historically-hard cards) first, then, if count isn't filled, padded out with not-yet-due cards in the same priority order — rather than a separate, duplicated sampling algorithm. An optional studentId samples from that student's own personal deck (joined shared decks + directly-reviewed cards, see Feature 7) instead of the shared default pool. The response exposes each sampled card's front only — back is withheld until it's graded.

    POST /quiz/:id/answer { cardId, answer } grades the response. Grading approach: a simple case-insensitive, whitespace-trimmed exact match against the card's back text (both sides lowercased, trimmed, and whitespace-collapsed before comparing) — no fuzzy matching, synonym handling, or partial credit. This is deliberately the simplest thing that could work; see FRICTION_LOG.md for the tradeoff.

    GET /quiz/:id/results returns a score summary — usable mid-quiz (a partial score) or once every sampled card has been answered (complete: true) — including exactly which cards were missed, with their prompt/answer, so a student can review what they got wrong right after finishing.

    curl -X POST localhost:4466/quiz/start -H "Content-Type: application/json" -d '{"count": 5, "studentId": "alice"}'
# -> { "id": "...", "cards": [ { "cardId": "...", "front": "What is meiosis?" }, ... ] }

curl -X POST localhost:4466/quiz/<quizId>/answer -H "Content-Type: application/json" -d '{
  "cardId": "<cardId>", "answer": "a process of cell division that produces gametes"
}'
# -> { "correct": true } or { "correct": false }

curl localhost:4466/quiz/<quizId>/results
# -> { "total": 5, "answered": 3, "correct": 2, "complete": false, "missed": [ {"cardId": "...", "front": "...", "back": "...", "submittedAnswer": "..."} ] }

    9. Due-card reminder digest¶

    GET /reminders/digest?studentId= returns a compact, single-paragraph summary of that student's own due queue — built from the exact same per-student due/leech logic Features 7 and 8 use, so it can't drift out of sync with what the student would actually see — designed to be easy for another service or a voice assistant to read aloud directly, e.g. "You have 5 cards due today, including 2 leeches." The response also includes the structured counts the sentence is built from (due, dueLeeches, totalLeeches, totalCards), for a caller that wants to render its own UI instead of just reading the sentence.

    curl "localhost:4466/reminders/digest?studentId=alice"
# -> {
#      "studentId": "alice",
#      "summary": "You have 5 cards due today, including 2 leeches.",
#      "counts": { "due": 5, "dueLeeches": 2, "totalLeeches": 3, "totalCards": 12 }
#    }

    10. Adaptive new-card generation bias¶

    PATCH /sessions/:id/segments now accepts an optional studentId. When given, appending new material biases flashcard generation toward topics that student has historically struggled with. The exact heuristic:

    1. A topic (one of a card's heuristic tags, see Feature 3 in the previous round) counts as weak for a student if, across every card of theirs (joined or directly reviewed) carrying that tag, the average ease factor is below 2.0 (meaningfully under scheduler.ts's 2.5 baseline) — or at least one of those cards is currently flagged a leech. A leech alone is enough regardless of average ease, since three failures in a row is a stronger signal than a merely-below-average ease factor (the same priority priority.ts already gives leeches over ease elsewhere).
    2. The topics of just the newly appended segments (not the full transcript) are extracted the same way any other ingest does (topics.ts).
    3. If any of those overlap the student's weak topics, up to 3 extra simple cloze-deletion cards (fill-in-the- blank, blanking the longest word in each new sentence) are generated from the new segments alone and added on top of whatever the generator's normal Q&A/definition/cloze tiers already produced for the full transcript — so a weak topic visibly yields more review material than a topic the student is already acing, which produces nothing extra.
    # alice previously failed several "photosynthesis"-tagged cards -> that topic is now "weak" for her
curl -X PATCH localhost:4466/sessions/<sessionId>/segments -H "Content-Type: application/json" -d '{
  "studentId": "alice",
  "segments": "Photosynthesis also depends on chlorophyll concentration in the leaf."
}'
# -> "newFlashcards" includes both whatever the normal tiers found AND a few extra
#    "Fill in the blank: ..." cards from just this new sentence, because photosynthesis is weak for alice.
# The same PATCH with no studentId (or a studentId with no weak topics) yields only the normal-tier cards.

    See FRICTION_LOG.md for this heuristic's real limitations (topic granularity, cold-start behavior, and why "more cards" rather than "simpler cards" was the chosen bias).

    Round 4: streaks & gamification, session planner, import round-trip, regenerate-a-card¶

    A fourth pass added four more features, each independently tested in test/smoke.test.ts (search for "Feature 11" through "Feature 14").

    11. Study streaks & gamification¶

    Every review submitted with a studentId (POST /review/:cardId { grade, studentId }) now also folds into that student's daily streak (see streak.ts). A "streak day" is any UTC calendar day on which the student completed at least one review — reviewing ten cards in one sitting only counts once. Consecutive streak days grow currentStreak; a day with zero reviews breaks it: the next review resets currentStreak back to 1 (the day it happens on still counts), but longestStreak only ever grows, never shrinks. Milestone badges (3-day-streak, 7-day-streak, 30-day-streak) are earned based on longestStreak, so once earned a badge is never revoked just because the current streak later resets — the same "permanent achievement" model most habit trackers use.

    GET /students/:studentId/streak returns the current state; a student who has never reviewed anything gets a valid all-zero response rather than a 404 (asking about a streak that hasn't started isn't an error).

    curl localhost:4466/students/alice/streak
# -> { "studentId": "alice", "currentStreak": 4, "longestStreak": 12, "badges": ["3-day-streak", "7-day-streak"], "lastActiveDate": "2026-03-04" }

    Note: since streaks are keyed off a studentId, only reviews submitted through the shared-decks studentId path count toward one — the original, student-less "default reviewer" endpoint (POST /review/:cardId with no studentId) has no single student to credit and never touches streak state.

    12. Global daily review session planner¶

    GET /review/session?studentId=&maxCards=<n> builds one bounded "here's your review for today" session across every deck a student has — their own directly-reviewed cards and every shared deck they've joined (Feature 7) — in the exact same adaptive priority order GET /review/due already uses (priorityScore/sortByPriority), then caps the result at maxCards. This is deliberately a thin wrapper around the existing per-student due-card query, not a new ranking algorithm: the planner's job is the cap and the "how many are left for later" count (totalDue), not a different ordering. A leech or badly-overdue card from one deck still outranks a merely-due card from another, so capping never means silently dropping the most urgent material.

    curl "localhost:4466/review/session?studentId=alice&maxCards=15"
# -> {
#      "studentId": "alice", "maxCards": 15, "totalDue": 42,
#      "cards": [ /* up to 15 PersonalFlashcardView objects, worst-priority first, across every deck alice has */ ]
#    }

    13. Import round-trip¶

    POST /import { tsv, sessionId?, title? } is the inverse of GET /export/GET /sessions/:id/export: it parses a TSV in that exact format (front, back, tags, header optional — see fromPortableTsv in export.ts) and creates flashcards from it, so a student can back up a deck and restore it later, or migrate cards between environments (a local dev instance and a deployed one, say). Pass sessionId to import into an existing session; omit it to create a fresh one (the "restore a full backup" shape).

    Deduplication, exactly as documented: a row is skipped (counted in skippedDuplicates, not created) if its trimmed, lowercased front text matches either (a) a flashcard the target session already has, or (b) an earlier row already accepted from this same import batch. That second half matters even for a brand-new session: a TSV with an accidental duplicate row still only produces one card. Imported cards always start with fresh scheduling/leech state (interval: 0, no leech history) — a TSV export carries no review history to restore, only front/back/tags survive the round trip (see FRICTION_LOG.md).

    # Back up a deck
curl localhost:4466/sessions/<sessionId>/export -o backup.tsv

# ...later, or in a different environment: restore it into a brand-new session
# (jq builds the JSON body so the TSV's tabs/newlines are escaped correctly)
jq -Rs '{tsv: .}' backup.tsv | curl -X POST localhost:4466/import -H "Content-Type: application/json" -d @-
# -> { "session": {...}, "imported": [ ...new Flashcard objects... ], "skippedDuplicates": 0 }

# Re-importing the same backup into the same session is a safe no-op
jq -Rs --arg sid "<sessionId>" '{tsv: ., sessionId: $sid}' backup.tsv | curl -X POST localhost:4466/import -H "Content-Type: application/json" -d @-
# -> "imported": [], "skippedDuplicates": <row count>

    14. Regenerate-a-card¶

    POST /flashcards/:cardId/regenerate re-runs flashcard generation to produce an alternative phrasing for one existing card, replacing its front/back in place. Everything else — id, tags, and every bit of spaced-repetition/leech state (interval, easeFactor, repetitions, dueAt, consecutiveFailures, isLeech) — is carried over untouched, so regenerating a confusingly-worded card doesn't cost a student their progress on it.

    It reuses the same injected FlashcardGenerator every other ingestion path uses — no separate regeneration logic. The only new piece is recovering which part of the session's transcript the card came from (findUnderlyingSegments in studyService.ts), so regeneration runs the generator over just that material instead of the whole session (which would just reproduce the same card set the original ingest already did). This exploits how each generator tier builds a card's text: a Q&A card's front/back are the two source segments' text verbatim, so an exact match recovers them exactly; a cloze card's blanked word can be substituted back in to reconstruct the original sentence and locate it; a definition card only has "the segment mentioning the term" as a fallback signal, since its front is reworded rather than verbatim. If the generator's normal tiers produce nothing different for that material (a real possibility for terse source text), regeneration falls back to generateClozeCards — the same exported helper Feature 10's adaptive bias already reuses — for a guaranteed-different fill-in-the-blank phrasing, rather than writing a second cloze generator.

    curl -X POST localhost:4466/flashcards/<cardId>/regenerate
# -> the same card id, with a fresh front/back and identical interval/easeFactor/dueAt/isLeech

    Round 5: concept graph, Feynman mode, study-guide synthesis, exam readiness¶

    The first four rounds were product-completeness features (quiz mode, streaks, import/export). This round is four features chosen specifically to be genuinely novel study-coaching functionality — not more infrastructure hardening — each independently tested in test/smoke.test.ts (search for "Feature 15" through "Feature 18").

    15. Concept graph¶

    GET /concepts/:name answers "show me everything related to X," across every session and deck, built from real text analysis of existing flashcard content — not a manual tagging system a caller populates. conceptGraph.ts extracts 1-2 lightweight "concept" strings from a single card's own front/back, in three tiers:

    1. Definition-style fronts ("What is/are <X>?") — this covers both flashcardGenerator.ts's tier-2 definition cards and any tier-1 Q&A card whose source question happened to be phrased that way — yield the defined term/noun phrase itself (e.g. mitochondrion, or the powerhouse of the cell).
    2. Cloze cards ("Fill in the blank: ...") yield the blanked word/phrase — the card's own back — as the concept.
    3. Any other Q&A pair yields the highest-scoring significant word(s) shared across its front and back, using the same word-frequency + capitalization-bonus heuristic topics.ts already uses for a whole transcript, just scoped to one card's two fields.

    This is what makes it a real graph: two cards from entirely different sessions ingested weeks apart — one a "What is Mitochondrion?" definition card, the other a "What does Mitochondrion do?" generic Q&A pair from an unrelated deck — both resolve to the concept mitochondrion and surface together, with no link ever created by hand.

    curl localhost:4466/concepts/mitochondrion
# -> { "concept": "mitochondrion", "cards": [ { "cardId": "...", "sessionId": "...", "sessionTitle": "...",
#                                                "front": "...", "back": "...", "tags": [...] }, ... ] }

    16. Feynman/peer-teaching explanation mode¶

    POST /review/:cardId/explain { explanation, studentId? } is the "explain it to learn it" technique: instead of self-grading with the four-point scale, a student submits a free-text explanation of the card's concept in their own words, and StudyLoop grades it against the card's actual back content with a real (heuristic, LLM-free) key-term rubric in explainGrader.ts — not string equality. It extracts the answer's significant key terms, checks which ones the explanation mentions (after light stemming on both sides, so "cells" credits "cell" and "photosynthesizes" credits "photosynthesis"), and reports exactly which terms were covered and which were missing.

    The derived coverage score is mapped onto the same RecallGrade vocabulary (score >= 0.85 → easy, >= 0.5 → good, >= 0.25 → hard, else again) and run through the exact same scheduling/leech machinery a normal grade would (recordReview/recordReviewForStudent) — so a weak explanation genuinely reschedules the card and can push it toward becoming a leech (or clear one), rather than being a side channel that only returns feedback text with no effect on the review queue. It works on any card, not just ones already flagged as leeches — the leech/adaptive signals already tracked elsewhere are what make this mode worth reaching for on a card a student keeps failing, not a precondition the API enforces.

    curl -X POST localhost:4466/review/<cardId>/explain -H "Content-Type: application/json" -d '{
  "explanation": "Mitochondria are the part of the cell that makes energy the cell can use."
}'
# -> { "grade": "good", "score": 0.71, "passed": true,
#      "matchedTerms": ["mitochondria", "energy", "cell"], "missingTerms": ["respiration"],
#      "feedback": "Good start — you covered mitochondria, energy, cell, but missed mentioning respiration.",
#      "card": { ...rescheduled exactly like a normal "good" grade... } }

    17. Cross-session study guide synthesis¶

    GET /topics/:topic/study-guide merges every session tagged with topic (see Feature 3's heuristic tagging) into one consolidated study guide — a real union-of-material synthesis (studyGuide.ts), not a raw concatenation of their summaries:

    • Each session's auto-generated summary has its per-session boilerplate prefix ("Session covered N statement(s) across K speaker(s).", meaningless once merged) stripped, is split into sentences, and every sentence is deduplicated by a normalized key against every other session's — so two sessions that happened to restate the same fact contribute it to the guide once, not twice.
    • concepts is the union of every concept extractConceptsFromCard (Feature 15's concept graph) resolves across every flashcard in every one of these sessions, deduplicated the same way.
    curl localhost:4466/topics/ribosome/study-guide
# -> { "topic": "ribosome", "sessionCount": 2, "cardCount": 5,
#      "sessions": [ {"id": "...", "title": "Cell biology deep dive"}, {"id": "...", "title": "Protein synthesis review"} ],
#      "combinedSummary": "Ribosome is the cellular structure that synthesizes proteins. ...",
#      "concepts": ["messenger rna", "protein synthesis", "ribosome", ...] }

    18. Exam readiness score¶

    GET /topics/:topic/readiness?studentId= returns a composite, explainable 0-100 exam-readiness score (readiness.ts) combining three signals already tracked elsewhere in the store — no new state invented:

    score = notDueFraction * 50        // share of cards NOT currently due — SM-2 pushed them out because
                                    // they've been recalled reliably; entirely-overdue scores 0 here
      + recentPerformance * 35     // each graded card's quality (again=0/hard=0.4/good=0.75/easy=1),
                                    // weighted by exponential recency decay (14-day half-life) — a
                                    // grade from yesterday counts far more than one from months ago
      + streakFactor * 15          // min(currentStreak, 7) / 7 — consistent daily review is a real
                                    // signal independent of any one card's own state

    With studentId, it reads that student's own personal deck (joined decks + directly-reviewed cards) and their own study streak; without it, the shared student-less pool with no streak signal. The response always includes a plain-language reasons breakdown of what's dragging the score down — e.g. "12 cards overdue", "3 leeches unresolved", "no active study streak" — rather than a bare number a student has to guess at.

    curl "localhost:4466/topics/thermodynamics/readiness?studentId=alice"
# -> { "topic": "thermodynamics", "studentId": "alice", "score": 62, "cardCount": 14, "dueCount": 3,
#      "overdueCount": 2, "leechCount": 1, "notDueFraction": 0.79, "recentPerformance": 0.68, "streakDays": 4,
#      "reasons": ["2 cards overdue", "1 leech unresolved"] }
