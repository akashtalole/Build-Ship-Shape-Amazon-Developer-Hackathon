    CourtSide — AI Co-Commentator Backend for Live Sports¶

    Implementation of the "CourtSide" idea from hackathon-ideas/fire-tv.md: casual sports viewers tune out of unfamiliar or lower-profile games because they lack context — the rules, the players, what's actually at stake in the moment. CourtSide is an AI co-commentator that sits alongside a live sports broadcast, narrating plays in plain language and answering spoken or typed questions ("why was that a foul?", "what's the score?") without the viewer ever leaving the video.

    Built for the Fire TV track of the Build, Ship, Shape: Amazon Developer Hackathon.

    Scope of this submission¶

    This repo is the backend commentary service a Fire TV app's on-screen overlay would call — not the Fire TV app itself. The sandboxed environment this was built in can't run a Fire OS/Vega TV app, an Android emulator, or a physical Fire TV device, so this submission focuses on the part that's genuinely testable headlessly: game-state tracking, play-by-play event ingestion, and the two AI seams (event commentary + viewer Q&A) that a real Bedrock call would sit behind.

    What the real Fire TV integration would look like: a Vega/Fire OS video app renders the live stream full-screen with a lightweight overlay panel (a persistent caption strip plus an expandable panel, positioned to never cover the score bug or the ball/puck) that polls GET /games/:id/commentary and renders new lines as they arrive, auto-hiding during high-action stretches so it never blocks the play. A computer-vision pipeline watching the broadcast feed (or a paired play-by-play data API) would POST detected plays to POST /games/:id/events in real time. D-pad and voice input both wire into the same POST /games/:id/ask — pressing a "Ask CourtSide" remote button or a wake-word-driven voice query both just collect a question string and hit that one endpoint, so the front end doesn't need two separate answer paths for the two input modalities.

    How it works¶

    1. A game starts tracking (POST /games) — team names, sport (default basketball), and initial clock/period.
    2. Plays stream in (POST /games/:id/events) — this is the computer-vision/data-feed integration point. Each event (score, foul, turnover, rebound, steal, block, timeout, period_end, game_end) updates the running score/clock/period and immediately produces a line of commentary via the CommentaryProvider seam.
    3. The overlay polls state and commentary (GET /games/:id/state, GET /games/:id/commentary) to render the score bug and the narration feed (newest first).
    4. A viewer asks a question (POST /games/:id/ask) — answered by the same CommentaryProvider seam, grounded in the game's current score, period, clock, and recent plays.

    Advanced features¶

    Six additions on top of the v1 golden path, aimed at the kind of production concerns that show up the moment a demo service is asked to run for real: pushing updates instead of making every client poll, surviving a flaky upstream feed, controlling AI cost/latency at scale, personalizing output per viewer, resuming a feed after a disconnect, and protecting an LLM-shaped endpoint from abuse.

    1. Live commentary push via Server-Sent Events¶

    GET /games/:id/stream opens a long-lived text/event-stream connection and pushes a data: {...} line the moment a new event produces commentary — no polling needed for a client that wants to react instantly. The existing GET /games/:id/commentary polling endpoint is untouched, so an overlay can use either (or both: SSE for instant reaction, polling as a fallback/resync). Implemented with a tiny in-process pub/sub (src/pubsub.ts, one EventEmitter per game) — ingestEvent publishes after a non-duplicate event is processed; the route subscribes on connect and unsubscribes on req.on("close").

    # In one terminal: hold a stream connection open and print every push
curl -N localhost:4455/games/<id>/stream

# In another terminal: ingest an event — the first terminal immediately prints a
# "data: {"type":"commentary","commentary":{...},"state":{...}}" line
curl -X POST localhost:4455/games/<id>/events -H "Content-Type: application/json" \
  -d '{"type": "score", "team": "home", "points": 2}'

    2. Idempotent event ingestion¶

    POST /games/:id/events accepts an optional externalEventId — the upstream feed's own ID for the play. Re-posting the same externalEventId for the same game is a clean no-op: the original event/commentary is returned, the score is not double-applied, no second commentary line is generated, and nothing is re-published to the SSE stream. The response status distinguishes the two cases (201 for a new event, 200 with "duplicate": true for a replay) so a caller can tell them apart if it cares, without either case being an error. This is the standard defense against a webhook/event-ingestion endpoint getting double-posted by a flaky computer-vision pipeline or data feed.

    curl -X POST localhost:4455/games/<id>/events -H "Content-Type: application/json" \
  -d '{"type": "score", "team": "home", "points": 3, "externalEventId": "cv-play-042"}'
# Reposting the exact same externalEventId (network retry, at-least-once delivery, etc.)
# returns 200 { "duplicate": true, ... } instead of scoring the play twice.

    3. Confidence-gated commentary generation (sidecar-style fast path)¶

    Not every play needs a full (potentially LLM-backed, per-call-cost) CommentaryProvider round trip. isNotableEvent in src/gameService.ts is a small, explicit heuristic: a game_end always escalates; a score escalates only when it changes who's leading or ties a previously-decided game (a go-ahead/momentum-shifting score); a foul escalates only when its description flags it as serious (flagrant/technical/ejection); everything else (turnover, rebound, steal, block, timeout, period_end) is routine enough to template directly. Routine events call TemplateCommentaryProvider directly (the fast path); notable events go through the configured provider (the escalated path — a real Bedrock provider in production). Both paths are counted per game and exposed via GET /games/:id/metrics, mirroring a real cost/latency-optimization pattern for AI-generated commentary at scale.

    curl localhost:4455/games/<id>/metrics
# -> { "gameId": "...", "fastPathCount": 11, "escalatedCount": 3, "total": 14 }

    4. Personalized commentary preferences¶

    POST /games/:id/viewers/:viewerId/preferences stores a per-viewer { favoriteTeam, verbosity } object (verbosity is "concise" — the default, unchanged output — or "detailed"). personalizeText in src/commentaryProvider.ts applies those preferences as a post-processing decorator on top of whatever text was already generated (template or LLM alike): a matching favoriteTeam gets an appended fan-perspective note (e.g. "Celtics fan view: up by 3."), and "detailed" appends period/clock/score context. It's opt-in and additive — GET /games/:id/commentary with no viewerId and POST /games/:id/ask with no viewerId behave exactly as before.

    curl -X POST localhost:4455/games/<id>/viewers/v1/preferences -H "Content-Type: application/json" \
  -d '{"favoriteTeam": "Celtics", "verbosity": "detailed"}'

curl "localhost:4455/games/<id>/commentary?viewerId=v1"
# -> "...Tatum scores! ... (Celtics fan view: up by 3.) [Quarter 1, 11:42 remaining, Lakers 0 - 3 Celtics.]"

    5. Resumable commentary feed¶

    GET /games/:id/commentary accepts ?since=<cursor>, where <cursor> is either a previously-seen commentary line's id or an ISO timestamp. An ID cursor returns everything strictly newer than that entry (exact — unaffected by clock resolution, since it's resolved by position in the stored feed, not by comparing timestamps); a timestamp cursor returns everything created after it. A reconnecting client (or a Fire TV app resuming from the background) remembers the last commentary id it saw and passes it back instead of re-fetching full history every time.

    curl "localhost:4455/games/<id>/commentary?since=<last-seen-commentary-id>"

    6. Rate limiting on /ask¶

    POST /games/:id/ask now accepts an optional viewerId in the body. Questions are capped at 10 per 60-second window, keyed by (gameId, viewerId) when a viewerId is given, or (gameId, IP) otherwise — so a busy show still lets every viewer ask their own questions, but one spammy remote/voice loop can't flood the (potentially LLM-backed) Q&A path. The 11th question within the window gets a 429 with a clear message and a retryAfterMs hint instead of a silent drop or an expensive extra provider call.

    curl -X POST localhost:4455/games/<id>/ask -H "Content-Type: application/json" \
  -d '{"question": "what is happening", "viewerId": "v1"}'
# -> 429 { "error": "Too many questions for this game — limit is 10 per 60s. ...", "retryAfterMs": 4213 }

    Round 3: archive, alerts, and a cross-game watchlist¶

    Four more additions, all building directly on top of the confidence-gating work from round 2 rather than duplicating it: a shareable highlight reel, outbound webhook alerts for notable moments, a multi-game "what did I miss" view, and the idempotency/rate-limiting discipline those alerts need to be safe to turn on.

    1. Game archive & highlights¶

    GET /games/:id/highlights returns a shareable recap of a game's notable moments — and reuses the exact same isNotableEvent heuristic from round 2's confidence-gated commentary routing (src/gameService.ts) rather than a second, separate notion of "highlight-worthy". Every notable event is now also appended to an uncapped per-game highlight reel (src/store.ts's notableEventsByGame, distinct from the capped recentEvents used for the live overlay) the moment ingestEvent decides it's notable — so the endpoint works identically whether the game is still in progress (highlights-so-far) or has already received a game_end event (game_end is always notable, so it's always the top entry in a finished game's recap).

    curl localhost:4455/games/<id>/highlights
# -> { "gameId": "...", "status": "in_progress", "homeScore": 8, "awayScore": 6,
#      "highlights": [ { "event": {...}, "commentary": {...} }, ... ] }  // newest first

    2. Outbound score-alert subscriptions¶

    POST /games/:id/subscriptions { "callbackUrl": "https://...", "viewerId"?: "..." } registers a webhook that gets a signed POST the instant a notable event happens in that game — the same notability signal driving highlights above. The response includes a freshly generated per-subscription secret (subscription.secret), returned exactly once, that the receiver uses to verify each delivery.

    Delivery (src/webhooks.ts) is fire-and-forget from ingestEvent's point of view — the ingestion request that triggered a notable event returns immediately regardless of how the webhook delivery goes. Each delivery is signed with HMAC-SHA256 over the raw JSON body using the subscription's secret, sent as X-CourtSide-Signature: sha256=<hex-digest> (the same algo=digest convention GitHub/Stripe webhooks use). A failing delivery (non-2xx response or a network error) is retried up to 3 attempts total, with exponential backoff (150ms, then 300ms) between attempts, before being given up on and logged.

    # Register a webhook (note the returned "secret" — you'll need it to verify deliveries)
curl -X POST localhost:4455/games/<id>/subscriptions -H "Content-Type: application/json" \
  -d '{"callbackUrl": "https://example.com/courtside-alerts"}'
# -> 201 { "subscription": { "id": "...", "callbackUrl": "...", "secret": "a3f1...c9", "createdAt": "..." }, "duplicate": false }

# Verify a delivery on the receiving end (Node example):
#   const expected = crypto.createHmac("sha256", secret).update(rawBody).digest("hex");
#   if (`sha256=${expected}` !== req.headers["x-courtside-signature"]) reject();

    3. Multi-game watchlist¶

    GET /watchlist?viewerId=<id> answers "what did I miss across every game I'm following?" — it aggregates notable events across every game that viewer has interacted with (asked a question on via POST /games/:id/ask, or set preferences for via POST /games/:id/viewers/:viewerId/preferences), ordered newest-first across games rather than grouped per game. A viewer who hasn't interacted with any game yet gets an empty (not error) watchlist.

    curl "localhost:4455/watchlist?viewerId=v1"
# -> { "viewerId": "v1", "gameIds": ["game-a", "game-b"],
#      "highlights": [ { "gameId": "game-b", "homeTeam": "...", "awayTeam": "...", "event": {...}, "commentary": {...} }, ... ] }

    4. Idempotent, rate-limited subscriptions¶

    POST /games/:id/subscriptions is idempotent on (gameId, callbackUrl) — the same spirit as round 2's externalEventId ingestion idempotency. Registering the same callbackUrl for the same game twice returns the original subscription (200, "duplicate": true, same id and secret) rather than creating a second one that would double-fire every future alert.

    Each subscription is also capped at 5 alert deliveries per rolling 60-second window (reusing the same fixed-window checkRateLimit from src/rateLimiter.ts that powers /ask's rate limiting, keyed per subscription instead of per viewer). A burst of notable events beyond the cap — several quick go-ahead scores, say — has its excess deliveries dropped for that subscription rather than queued or batched: the receiver never gets flooded, and nothing is actually lost, since the full, uncapped notable-event history is always available afterward via GET /games/:id/highlights. See FRICTION_LOG.md for why "drop" was chosen over "batch" here.

    # Registering the same callback twice is a no-op, not a second subscription:
curl -X POST localhost:4455/games/<id>/subscriptions -H "Content-Type: application/json" \
  -d '{"callbackUrl": "https://example.com/courtside-alerts"}'
# -> 200 { "subscription": { ...same id and secret as the first registration... }, "duplicate": true }

    Round 4: season stats, catch-up recaps, multi-sport, player alerts¶

    Four more additions: aggregating stats beyond a single game, a natural-language "what did I miss" recap for a window instead of raw commentary lines, generalizing the event vocabulary/templates to more than basketball, and narrowing the round-3 webhook subscription down to a single favorite player.

    1. Season-long stats aggregation¶

    GET /stats/team/:teamName and GET /stats/player/:playerName return cumulative totals — points, an eventCounts breakdown per event type, notableEvents, and gamesPlayed — aggregated across every game this process has ingested events for, not just one. Every non-duplicate event folds into whichever team/player it names the instant ingestEvent processes it (recordTeamStat/recordPlayerStat in src/gameService.ts), keyed by a trimmed, case-insensitive name so "Lakers" ingested as the home team in one game and the away team in another still accumulates under one entry. A name that's never appeared in an event returns a zeroed result (200), not a 404 — there's no separate "team" or "player" resource to have gone missing.

    curl localhost:4455/stats/team/Lakers
# -> { "name": "Lakers", "gamesPlayed": 2, "points": 13, "eventCounts": { "score": 2, "foul": 1 }, "notableEvents": 1 }

curl localhost:4455/stats/player/James
# -> { "name": "James", "gamesPlayed": 2, "points": 13, "eventCounts": { "score": 2, "foul": 1 }, "notableEvents": 1 }

    2. "Catch-up" recap endpoint¶

    GET /games/:id/recap generates a natural-language summary of a window of the game — via the exact same CommentaryProvider seam that narrates events and answers questions (a real Bedrock provider would summarize it; TemplateCommentaryProvider's new generateRecap gives a deterministic fallback) — instead of just handing back the raw commentary lines the way GET /games/:id/commentary does. The window is expressed either as ?sinceMinutes=<n> (a rolling time window ending now) or ?since=<commentary-id-or-ISO-timestamp> (the same cursor style GET /games/:id/commentary?since= already uses — an id resolved by position, exact; a timestamp as a best-effort fallback); since wins if both are given, and omitting both recaps the whole game so far. Building this required giving each game its own uncapped, chronological event log (allEventsByGame in src/store.ts) alongside the capped recentEvents the live overlay uses — the same "capped list isn't an archive" lesson round 3's highlights feature already ran into, applied to raw events instead of just notable ones.

    curl "localhost:4455/games/<id>/recap?sinceMinutes=10"
# -> { "gameId": "...", "windowLabel": "in the last 10 minutes", "eventCount": 4,
#      "summary": "Catching you up on what happened in the last 10 minutes: ...", "generatedAt": "..." }

curl "localhost:4455/games/<id>/recap?since=<last-seen-commentary-id>"

    3. Multi-sport event vocabulary¶

    A game can declare "sport": "basketball" | "football" | "soccer" at POST /games (any other value, or none, keeps basketball's exact original behavior — the default sport was already basketball since round 1). Two things now adapt per sport instead of hardcoding basketball's vocabulary:

    • Commentary phrasing (src/commentaryProvider.ts): each event type (score, foul, turnover, rebound, steal, block, game_end) has its own per-sport phrase set — a soccer score says "GOAL! ... finds the back of the net" instead of "Bucket for ...", a football foul says "Penalty on ..." instead of "Foul called on ...", and a soccer game ends with "That's full-time!" instead of "That's the final!". A game's default periodLabel is now sport-aware too — "half" for soccer, "quarter" for basketball and football (basketball's original default, unchanged).
    • The isNotableEvent foul-escalation gate (src/gameService.ts): basketball's serious-foul keywords (flagrant/technical/ejection) don't mean anything in soccer or football. isSeriousFoulDescription now branches per sport — soccer escalates on "red card"/"second yellow"/"violent conduct", football on "flagrant"/"ejection"/"targeting"/"unnecessary roughness"/"unsportsmanlike" — so a soccer foul description that happens to say "reaching-in foul" (a basketball phrase, e.g. from a feed that reuses descriptions loosely) doesn't spuriously escalate, and a real red card does.

    GET /games/:id/recap reuses the sport-neutral describeEvent helper (already just [type] who +points — description, no sport-specific words), so recaps adapt to any sport for free without needing their own per-sport phrasing.

    curl -X POST localhost:4455/games -H "Content-Type: application/json" \
  -d '{"sport": "soccer", "homeTeam": "Barca", "awayTeam": "Real"}'
# -> periodLabel defaults to "half" instead of "quarter"

curl -X POST localhost:4455/games/<id>/events -H "Content-Type: application/json" \
  -d '{"type": "score", "team": "home", "player": "Messi", "points": 1}'
# -> "GOAL! Messi finds the back of the net! Barca 1 - 0 Real." (never "basket"/"bucket"/"free throw")

    4. Player-level alert subscriptions¶

    POST /games/:id/subscriptions now accepts an optional playerName alongside callbackUrl. When set, that subscription only fires for a notable event whose player field matches (case-insensitively) — a fan who only cares about their favorite player's moments, not every notable event in the game. Omitting playerName keeps round 3's original behavior unchanged (every notable event in the game). The idempotency key (getOrCreateSubscription in src/store.ts) is now (gameId, callbackUrl, playerName) instead of just (gameId, callbackUrl), so the same callback URL can hold both a game-wide subscription and separate per-player ones without colliding, and re-registering the exact same (callbackUrl, playerName) pair is still idempotent.

    curl -X POST localhost:4455/games/<id>/subscriptions -H "Content-Type: application/json" \
  -d '{"callbackUrl": "https://example.com/curry-alerts", "playerName": "Curry"}'
# -> only fires for a notable event with "player": "Curry" — a flagrant foul on a different player is silent

    Project layout¶

    src/
  types.ts               Game/event/commentary data model, valid event-type vocabulary, preferences/metrics types,
                          NotableEventRecord (highlights), Subscription (webhook, now with an optional playerName

                           TemplateCommentaryProvider fallback + personalizeText (per-viewer preference decorator)
                           + per-sport phrase tables and the serious-foul vocabulary isNotableEvent uses per sport

                           commentary routing (isNotableEvent, now sport-aware), generate commentary, answer
                           questions, highlights, subscription registration (game- or player-scoped), cross-game
                           watchlist aggregation, season-long stats lookups, and the catch-up recap
  webhooks.ts             Outbound score-alert delivery: HMAC-SHA256 signing, retry with exponential backoff,
                           per-subscription rate capping, and player-name filtering before fan-out
  pubsub.ts               Per-game EventEmitter registry powering the SSE stream
  rateLimiter.ts           Fixed-window rate limiter shared by POST /ask and outbound webhook delivery
  server.ts                Express app factory: the HTTP API a Fire TV overlay would poll and stream
  index.ts                 Entry point
test/
  smoke.test.ts            End-to-end test over real HTTP: start game → ingest events → state/commentary →
                            Q&A → unknown-game 404s → invalid-event 400s → ordering guarantees → SSE push →
                            idempotent ingestion → fast/escalated routing → per-viewer personalization →
                            resumable feed → /ask rate limiting → highlights → signed webhook delivery →
                            idempotent subscriptions → per-subscription rate cap → multi-game watchlist →
                            season-long team/player stats → windowed catch-up recaps → sport-aware commentary
                            and notable-event heuristic → player-scoped alert subscriptions

    Running it¶

    npm install
npm run build
npm start
# CourtSide listening on http://localhost:4455

    Or for local iteration: npm run dev

    Try it by hand¶

    # 1. Start tracking a game
curl -X POST localhost:4455/games -H "Content-Type: application/json" \
  -d '{"homeTeam": "Hawks", "awayTeam": "Nets"}'
# -> note the returned "id"; use it as :id below

# 2. Ingest a few plays (stands in for a CV pipeline / play-by-play feed)
curl -X POST localhost:4455/games/<id>/events -H "Content-Type: application/json" \
  -d '{"type": "score", "team": "home", "player": "Trae", "points": 3}'

curl -X POST localhost:4455/games/<id>/events -H "Content-Type: application/json" \
  -d '{"type": "foul", "team": "away", "player": "Bridges", "description": "reaching-in foul"}'

# 3. Check the running state
curl localhost:4455/games/<id>/state

# 4. See generated commentary, newest first
curl localhost:4455/games/<id>/commentary

# 5. Ask a question grounded in current game state
curl -X POST localhost:4455/games/<id>/ask -H "Content-Type: application/json" \
  -d '{"question": "why was that a foul?"}'

    Testing¶

    npm test

    Starts the server on an ephemeral port and drives it over real HTTP requests: starting a game, ingesting four different event types (score, foul, turnover, score) and confirming each produces grounded commentary, confirming /state reflects the running score, and confirming /ask answers both a "what's the score?" and a "why was that a foul?" question using the actual game data. It also covers edge cases: an unknown game ID returns a clean 404 (not a crash) from both /state and /ask; an event with a missing or invalid type is rejected with 400; a score event missing a positive points field is rejected; an empty question is rejected; the commentary feed stays in newest-first order; and rejected events are confirmed to leave no trace in game state or the commentary feed.

    It then covers all six advanced features end to end: a client connected to GET /games/:id/stream receives a pushed SSE line the instant an event is ingested; replaying the same externalEventId produces no duplicate score mutation or commentary line; a routine event takes the fast template path while a go-ahead score and a flagrant foul both escalate, reflected exactly in GET /games/:id/metrics; a viewer's stored preferences visibly change both GET /games/:id/commentary?viewerId=... text and a personalized /ask answer while the un-personalized versions stay unchanged; ?since=<commentary-id> (and ?since=<timestamp>) returns only newer entries; and the 11th rapid question from one viewer in one game is rejected with 429 while a second viewer on the same game is unaffected. No external services required.

    It then covers all four round-3 features: GET /games/:id/highlights returns only the notable events out of a mixed sequence of routine/notable ones, both while the game is in progress and after game_end; a webhook registered via POST /games/:id/subscriptions (against a tiny local http.createServer the test spins up itself) receives a correctly HMAC-SHA256-signed POST the moment a notable event is ingested, and nothing at all for a routine one; registering the same callbackUrl twice returns the original subscription instead of creating a duplicate; a burst of 8 notable events against one subscription results in exactly 5 deliveries (the rate cap) with the rest dropped, while the full 8 still show up in that game's /highlights; and GET /watchlist?viewerId=... aggregates notable events across two different games one viewer interacted with (one via /ask, one via preferences), newest-first across games, with an empty (not error) result for a viewer with no interactions yet.

    Finally, it covers all four round-4 features: GET /stats/team/:teamName and GET /stats/player/:playerName correctly sum points/eventCounts/gamesPlayed for a team and player that appeared in two separate games (one as home, one as away), and return a zeroed result for a name never seen; GET /games/:id/recap?since=<cursor> summarizes only the event after the cursor (mentioning it by name) while never mentioning an earlier event outside the window, ?sinceMinutes= and no-window-at-all are also exercised; a soccer game's generated commentary is asserted to avoid basketball-specific words ("basket"/"bucket"/"free throw"/"boards") and its notable-event heuristic is shown using soccer's own serious-foul vocabulary (a basketball-phrased description stays routine, a "red card" escalates), while a game with no sport specified is confirmed to keep basketball's original periodLabel default unchanged; and a player-scoped subscription (playerName: "Curry") is shown firing for a notable event naming that player but staying silent for another player's notable event in the same game, with the same callbackUrl registering as a distinct subscription per player.

    Swapping in a real Bedrock-backed provider¶

    Everything in gameService.ts and server.ts depends only on the CommentaryProvider interface in src/commentaryProvider.ts (narrateEvent(game, event) and answerQuestion(game, question)) — not on TemplateCommentaryProvider directly. To go from template fallback to a real LLM:

    1. Write a BedrockCommentaryProvider implements CommentaryProvider that builds the same CommentaryPrompt shape the template provider builds internally (buildEventPrompt / buildQuestionPrompt, already exported) — a system persona, an instruction, and serialized context — and forwards system + instruction + context into a bedrock-runtime ConverseCommand (e.g. against an Anthropic Claude or Amazon Nova model on Bedrock), returning the model's text response.
    2. Swap the one line in src/index.ts that constructs new TemplateCommentaryProvider() for new BedrockCommentaryProvider(bedrockClient, modelId). Nothing in gameService.ts, server.ts, or the test suite needs to change, since both only ever call the interface.
    3. Optionally keep TemplateCommentaryProvider around as an automatic fallback (e.g. wrap the Bedrock call in a try/catch that falls back to the template provider) so the overlay never shows a broken/empty commentary line if a Bedrock call times out or the account has no model access during a live demo.

    This is deliberately the same boundary shape as alexa-homeops-mcp's device-control seam and ring-porchpass's RingClient — an interface plus a fully-working in-memory/simulated default, with the real integration isolated to one new file and one line in index.ts.

    Judging-criteria alignment¶

    • Tech Implementation: A real Express/TypeScript service with an actual game-state machine (score, period, clock, capped recent-events log), input validation that rejects malformed CV/feed events with 400s instead of corrupting state, and a genuine end-to-end HTTP test suite (not mocks) covering the golden path plus edge cases. The CommentaryProvider interface is deliberately shaped like a Bedrock Converse call (system + instruction + context in, text out) so wiring in a real model is a same-shaped swap, not a redesign.
    • Design: The API is shaped around exactly what a 10-foot overlay needs and nothing more — poll /state for the score bug, poll /commentary for the narration feed (newest first, so the overlay can just prepend), and a single /ask endpoint that both D-pad-driven typed questions and voice-transcribed questions can share, so the overlay doesn't need parallel code paths per input modality.
    • Potential Impact: Commentary generation and Q&A are entirely event/data-driven and sport-agnostic (the event vocabulary and sport/periodLabel fields aren't basketball-specific), so the same service could sit behind any live-sports overlay across leagues — matching the idea's "big-tent, cross-league companion layer" pitch — without a new backend per sport.
    • Quality of Idea: This backend is the concrete, buildable slice of a pitch that stacks three prioritized Fire TV categories (AI-enhanced viewing, sports, multi-modal UX) and pairs naturally with the AWS Builder mini-challenge (Bedrock for commentary generation) with genuinely near-zero added scope, since the seam this submission built is exactly where that Bedrock integration plugs in.
