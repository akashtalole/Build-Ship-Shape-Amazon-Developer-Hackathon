# Plan: Kiro IDE skills and Kiro Crew for building Amazon-device MCP apps

**Goal:** a repeatable Kiro setup for building apps like HomeOps: a self-hosted MCP server (TypeScript, Streamable
HTTP, protocol 2025-11-25) that an Alexa+ agent (or a Ring, Fire TV or Bee backend) calls, deployed on Amazon ECS
Express Mode, with Claude via MCP sampling, Amazon Bedrock or the Anthropic API.

Everything below encodes what this repo actually learned the hard way. The numbers in brackets point at entries in
[`alexa-homeops-mcp/FRICTION_LOG.md`](../alexa-homeops-mcp/FRICTION_LOG.md) or at fixes in `deploy/`.

> Kiro facts were checked against kiro.dev on 2026-11-27 (sources at the end). Kiro moves fast. Items marked
> **verify** were unclear or inconsistent in the docs; confirm them before relying on them.

## Two layers

| Layer | Kiro product | Job | Where config lives |
|---|---|---|---|
| **Build** | Kiro IDE (and Kiro CLI) | Turn an idea into a tested, deployable MCP server | Repo: `.kiro/` (steering, skills, specs, hooks, custom agents, MCP config) |
| **Run** | Kiro Crew | Watch the deployed app, run scheduled checks, keep the friction log, answer in Slack | Your machine: `~/.kiro/crew/` and `~/.kiro/agents/` |

**A naming note.** `hackathon-ideas/aws-builder.md` used "Kiro Crew" for a multi-agent build pipeline. Kiro now
ships a product with that name, and it's something else: an open-source, self-hosted personal agent that runs on
your own hardware, with a local dashboard, a `kirocrew` CLI, scheduled jobs and chat channels. This plan uses:
- **"the build crew"** for a team of Kiro IDE custom subagents (section 4)
- **Kiro Crew** for the product, used for operations (section 7)

## 1. Target layout

```
.kiro/
  steering/                  always-on and file-scoped rules (section 2)
  skills/<name>/SKILL.md     on-demand know-how, with scripts/ and references/ (section 3)
  agents/<name>.json         the build crew (section 4)
  hooks/<name>.json          automatic checks (section 5)
  settings/mcp.json          MCP servers Kiro itself uses while building (section 6)
  specs/<feature>/           requirements.md (or bugfix.md), design.md, tasks.md, generated by Kiro (section 8; path: verify)
kiro/
  PLAN.md                    this file
  crew/                      Kiro Crew assets, copied to ~/.kiro/crew/ by crew/sync.sh (section 7)
  power/                     the same skills packaged as an installable Kiro power (section 9)
```

## 2. Steering: the rules every session follows

Steering files are `.kiro/steering/*.md`. Front matter picks the inclusion mode: `inclusion: always` (default),
`fileMatch` with `fileMatchPattern`, `manual` (invoke with `#name` or `/name`), or `auto` (needs `name` and
`description`). Keep these short: they load into every matching request.

| File | Inclusion | Rules it carries |
|---|---|---|
| `product.md` | always | Who the app serves; the voice-first product bar: one question per turn, ask before spending, speak up proactively |
| `tech.md` | always | Node 20, TypeScript strict, `@modelcontextprotocol/sdk` (negotiates 2025-11-25), Express + Streamable HTTP, one `McpServer` per session, `/healthz`, zod schemas; never put secrets in env vars or code |
| `structure.md` | always | `src/tools/<domain>.ts` registers tools; `src/store.ts` owns data; `test/smoke.test.ts` drives a real MCP client; `deploy/` scripts; docs per project |
| `mcp-tools.md` | fileMatch `**/src/tools/**/*.ts` | Every tool has annotations (`readOnlyHint` etc.); `outputSchema` must match `structuredContent` exactly, including every field [4, 15]; spending tools confirm via elicitation [2]; model calls go through one `generateText()` chain [20] |
| `deploy.md` | fileMatch `deploy/**` | ECS Express rules learned in production: never pass `--monitor-mode` without `--monitor-resources`; create the cluster first; push a unique image tag per deploy; read the `endpoint` field; secrets via Secrets Manager [21, deploy fixes in #32, #33] |
| `voice.md` | auto | Keep what the voice agent sees to about 12 tools; hide admin tools with a profile, don't delete them [23] |

`AGENTS.md` at the repo root is also always loaded, so keep it as a short pointer to these files rather than a
second copy.

## 3. Skills: on-demand know-how

Skills are folders under `.kiro/skills/<name>/` with a `SKILL.md`. The front matter needs `name` (same as the
folder; lowercase, digits, hyphens) and `description` (what loads it); `scripts/` and `references/` are optional.
They load when the description matches the task, or explicitly with `/name`. Each one below packages a pattern
that already works in `alexa-homeops-mcp/`, so its `references/` can point at real code instead of prose.

| Skill | Loads when the task is… | Contains | Encodes |
|---|---|---|---|
| `mcp-server-scaffold` | starting a new MCP server | `scripts/scaffold.sh`: copies a trimmed HomeOps skeleton (index/server/store/one tool/test/Dockerfile) and renames it | Session-per-client transport, `/healthz`, Bearer token → tenant [6] |
| `mcp-tool-design` | adding or changing a tool | Checklist + annotated example tool; how to write `outputSchema` so it can't drift | [4, 15, 19] |
| `confirm-before-spend` | a tool spends money or changes the outside world | Elicitation request, fallback preview-then-confirm when the client can't elicit, idempotency key | [2] |
| `llm-fallback-chain` | a tool needs a language model | `generateText()`: MCP sampling, then Bedrock (`bedrock-mantle:CreateInference` / `AmazonBedrockMantleInferenceAccess`) or the Anthropic API (key from Secrets Manager), then a template | [20, 21, 22] |
| `voice-tool-profile` | the tool list grows, or before a demo | `registerTool` wrapper that calls `.disable()` on tools outside the profile; how to pick the 12 | [23] |
| `mcp-e2e-testing` | writing or fixing tests | Smoke-test pattern: real client over HTTP, isolated data dir, fake `fetch` endpoints for Bedrock/Anthropic, no mocked protocol calls | [5, 14, 19] |
| `ecs-express-deploy` | deploying or redeploying | Links `deploy/`; the known failure modes and what each error means; reading stopped-task reasons | #32, #33 |
| `live-mcp-check` | "is the deployed app working?" | `scripts/live-check.ts`: connects with a throwaway Bearer token (so demo data stays clean), checks version, tool count and which model path answered | The checks run by hand on 2026-10-22 |
| `devpost-submission` | preparing a hackathon entry | Eligibility checklist (public repo, real device or simulator, video under 3 minutes), write-up template, demo pipeline (`demo/`) | The October submission |
| `friction-log` | after hitting anything non-obvious | Entry format and examples | Every FRICTION_LOG entry |

**Order to write them:** `mcp-tool-design`, `mcp-e2e-testing`, `ecs-express-deploy`, `live-mcp-check` first.
These four cover the mistakes that cost the most time.

## 4. The build crew: custom subagents

Custom agents are `.kiro/agents/<name>.json` (Markdown also works), with fields including `name`, `description`,
`prompt`, `model`, `tools`, `resources`, `permissions` and `mcpServers`. The main agent delegates based on each
agent's `description` and needs `subagent` in its `tools`. Subagents run in parallel, each with its own context.

**Gotcha:** custom agents don't load steering or skills on their own. Each one lists them in `resources`, e.g.
`"file://.kiro/steering/**/*.md"` and `"skill://.kiro/skills/*/SKILL.md"`.

| Agent | Does | Tools | Gets |
|---|---|---|---|
| `mcp-architect` | Reviews `design.md`: tool surface, schemas, which tools the voice profile shows, what needs confirmation | read-only | steering, `mcp-tool-design`, `voice-tool-profile`, `confirm-before-spend` |
| `mcp-builder` | Implements spec tasks in `src/` | read, write, shell (`npm`, `npx tsc`) | steering, `mcp-tool-design`, `confirm-before-spend`, `llm-fallback-chain` |
| `test-engineer` | Writes and runs end-to-end tests for each task | read, write, shell (`npm test`) | steering, `mcp-e2e-testing` |
| `reviewer` | Gate before a task is marked done: checks the steering rules, secrets, IAM scope, the cost of new AWS resources | read-only | steering, all skills |
| `deploy-engineer` | The only agent allowed to run `deploy/` and `aws`; runs `live-mcp-check` afterwards | shell, with approval required for `aws` | `deploy.md`, `ecs-express-deploy`, `live-mcp-check` |
| `submission-writer` | READMEs, friction log, Devpost text, demo script | read, write | `friction-log`, `devpost-submission` |

**Flow for one feature:** spec → `mcp-architect` reviews the design → per task, `mcp-builder` and `test-engineer`
work in parallel → `reviewer` → deploy by a human or `deploy-engineer` (with approval) → `live-mcp-check`.

Example (`.kiro/agents/mcp-builder.json`, field names from the docs, values to tune):

```json
{
  "name": "mcp-builder",
  "description": "Implements MCP server tasks from a spec: tools, store functions, schemas. Use for any change under src/.",
  "prompt": "Implement the task you are given. Follow the steering rules. Run `npx tsc --noEmit` before finishing and report the result. Do not run deploy scripts or aws commands.",
  "tools": ["read", "write", "shell"],
  "resources": ["file://.kiro/steering/**/*.md", "skill://.kiro/skills/*/SKILL.md"],
  "includeMcpJson": true
}
```

The exact `tools` and `permissions` values are in the custom-agent configuration reference: **verify** them
before writing the files.

## 5. Hooks: checks that run without being asked

Hooks are `.kiro/hooks/<name>.json` with `version: "v1"` and a `hooks` array. Each hook has `name`, `trigger`, an
optional `matcher`, and an `action` of type `command` or `agent`.

| Hook | Trigger | Action |
|---|---|---|
| Typecheck on save | file save, matcher `src/.*\.ts$` | command: `npx tsc --noEmit` |
| Test after each spec task | `PostTaskExecution` | command: `npm test` |
| Guard destructive AWS commands | `PreToolUse` on the shell tool | command: a small script that blocks `teardown`, `aws ... delete*` and `secretsmanager` writes unless a human runs them |
| Friction-log nudge | `AgentStop` | agent: "If this session hit anything non-obvious, add a friction-log entry" |
| Live check | `Manual` | command: `npx tsx .kiro/skills/live-mcp-check/scripts/live-check.ts $URL` |

**Verify:**
- The trigger names. The docs' table and their own example disagree (`FileSave` vs `PostFileSave`), so create one
  hook in the Kiro UI and copy the JSON it writes.
- A community guide says hooks don't fire inside subagents. If so, subagents' quality gates must live in their
  prompts and in the main session's `PostTaskExecution` hook, not in per-file hooks.

## 6. MCP servers Kiro uses while building

Workspace `.kiro/settings/mcp.json`, top-level key `mcpServers` (it merges with `~/.kiro/settings/mcp.json`; the
workspace wins):

- **The app itself**, e.g. `{"url": "http://localhost:3333/mcp"}`, so Kiro can call the tools it's building, like
  dogfooding through Alexa+.
- **An AWS documentation MCP server**, for ECS, IAM and Bedrock questions, instead of answering from memory.
- **GitHub**, for PRs.

Secrets use `${VAR}` expansion, never literal values in the file.

## 7. Kiro Crew: running and watching the apps

What it is: a self-hosted, persistent personal agent. It runs on your machine, in a container, or on a server you
control. You reach it through a desktop app, a dashboard at `localhost:5476`, the `kirocrew` CLI, and chat
(Slack, Teams, Discord and others). It's personal, not a team service, and the docs describe no GitHub PR
triggers. So PR-level automation stays in the IDE, the CLI or GitHub Actions; Crew is for operations.

| Component | Where | Use |
|---|---|---|
| Agent `mcp-ops` | `~/.kiro/agents/mcp-ops.json` (`name`, `description`, `model`, `prompt`, `tools`) | Knows the deployed services, their URLs and the runbooks |
| Skills | `~/.kiro/crew/skills/<name>/SKILL.md` (front matter: `name`, `description`, `triggers`, `always`) | Copies of `live-mcp-check`, `ecs-express-deploy` (read-only parts), `friction-log` |
| Scheduled jobs | Schedule panel (natural language or cron) | Hourly: `/healthz` plus an MCP handshake and tool count. Daily: model-path check (alert if answers are coming from the template, which means Bedrock or the API key broke). Daily: "is anything still running that costs money?" (Fargate and the load balancer bill even when idle) |
| Hooks | `~/.kiro/crew/hooks.json`, `PreToolUse` | Deny teardown and `aws ... delete*` (exit code 2 denies) unless approved in chat |
| Approval mode | `agent.approval_mode` in `~/.kiro/crew/config.json` | `Interactive` for anything touching AWS |
| Chat | Slack channel | Alerts go out; "run the live check" comes in |

**Sharing with the IDE.** Crew reads `~/.kiro/crew/skills/`, not the repo's `.kiro/skills/`, and its skill front
matter adds `triggers`/`always`. `kiro/crew/sync.sh` should copy the shared skills over and add those fields. Keep
the repo copy as the source of truth.

**Limits:**
- Crewmates/bots, shared Crew and remote dispatch are preview features, off by default. The plan doesn't depend
  on them.
- Crew lists installed powers but doesn't load them yet, so it can't use the section 9 power.

## 8. Specs: how each new app or feature starts

Use **feature specs** (`requirements.md` → `design.md` → `tasks.md`) for new tools, and **bugfix specs**
(`bugfix.md`) for problems found in a live check. Running all tasks builds a dependency graph and runs independent
tasks in parallel waves, which suits the builder/tester split.

Add two required sections to every design, enforced by `mcp-architect`:
1. **Voice surface:** which tools the voice profile shows, and why that list stays near 12.
2. **Side effects:** every tool that spends money or contacts the outside world, and how it confirms first.

## 9. Package it as a Kiro power

Once the skills are stable, bundle them as a power so other repos can install them in one step. The power is a
directory with:
- `plugin.json`: the manifest with activation keywords, e.g. "alexa+", "mcp server", "voice tools", "ecs express"
- `skills/`: the skills from section 3
- `mcp.json`: the AWS documentation server

A power loads only when a task matches its keywords, which keeps unrelated sessions lean.

## 10. Rollout

| Phase | Deliverable | Done when |
|---|---|---|
| 1 | Steering (section 2) + the first four skills + `mcp.json` | In HomeOps, Kiro adds a small tool that passes `tsc`, has a matching `outputSchema` and annotations, and ships with a test, without being told the rules |
| 2 | Build crew (section 4) + hooks (section 5) | A full spec for a **new** app runs through the crew: **TripCopilot** (`hackathon-ideas/alexa-plus.md`, idea 4), from requirements to green tests |
| 3 | Deploy + Kiro Crew ops (sections 3 and 7) | TripCopilot is deployed with `deploy/`, and Crew's hourly check has run for a day and would have caught a broken model path |
| 4 | Power (section 9) | A fresh repo installs the power and scaffolds a working server with `mcp-server-scaffold` |

**Measure the pilot:** time from idea to green tests and the number of steering-rule violations `reviewer`
catches. Also count how many of the 23 friction-log mistakes recur. That number is the real test of whether the
skills work.

## 11. Open questions

- Hook trigger identifiers, and whether hooks fire inside subagents (section 5).
- The on-disk spec directory, and the Markdown format for custom agents.
- Whether Crew's `~/.kiro/agents/` JSON is the same format the IDE uses (section 7).
- How Alexa+ registers a self-hosted MCP server, and whether it supports sampling and elicitation. This was never
  confirmed during the hackathon. Write `alexa-plus-connect` as a skill after the first real connection, not before.
